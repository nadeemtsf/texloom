# Bounded runtime dependency review - updated 5 November 2026

**Later finding:** primary advisory/source reading identifies an unresolved security blocker against the current pinned distributor build. Public distribution remains blocked; see [DEPENDENCY-ADVISORY-REVIEW.md](DEPENDENCY-ADVISORY-REVIEW.md). The historical hash/publication-verification results below remain true within their scope and are not security approval. No replacement pin or binary was introduced while tests are paused.

Later source-only follow-up: [DEPENDENCY-SOURCE-REVIEW.md](DEPENDENCY-SOURCE-REVIEW.md) records the wheel's missing source hash and a pinned upstream build-repository/workflow inspection. It does not run builds, upstream tests or advisory scans, and does not close the nested-build/security/license gates. The owner has now paused all tests. The pin and prior cryptographic-verification results below are unchanged.

The current packaged verifier uses **PDFium 156.0.8076.0**, extracted from the SHA-256-pinned pypdfium2 5.14.0 Windows x64 wheel. Historical PDFium 126 / pypdfium2 4.30 development reports are different artifacts. The app's Rust worker does not require Python.

The [official package index](https://pypi.org/project/pypdfium2/5.14.0/) and its JSON endpoints were checked on 4 November 2026. The current package version at that check was 5.14.0; the exact Windows wheel digest matched the repository pin and cached wheel, its DLL matched the packaged DLL, all pinned notice entries were present, and the packaged notice matched its manifest. The wheel's PDFium version metadata reports no optional feature flags. This is distributor metadata, not an independent proof of every build option.

The 4 November review fetched/fingerprinted provenance metadata only. The 5 November follow-up used `pypi-attestations 0.0.31` with `sigstore 4.5.1`, default production trust and the explicit repository policy `https://github.com/pypdfium2-team/pypdfium2`. Verification of the exact pinned local wheel and captured PyPI provenance passed. A valid-ZIP copy with changed archive bytes failed the subject-digest check, and the original wheel under an intentionally wrong repository policy failed the repository check. The archives were verified as data; the tampered copy was neither installed nor loaded. The verified wheel's DLL is byte-identical to the r4 packaged DLL; no runtime pin/binary changed.

This authenticates signed publication under the selected policy, not a reproducible PDFium build or an audit of that workflow and every nested component. The verifier was installed only in an isolated development environment from official PyPI over TLS; exact downloaded tool/dependency wheel hashes and versions are retained. It was not independently audited. Seven public trust metadata files were retained after verification; one `root.json` directory entry could not be read, and an initial optional cache-copy attempt failed there. This partial post-verification snapshot is not a presealed trust environment. No signing or browser login was performed. [PyPI's attestation introduction](https://docs.pypi.org/attestations/) and the [verification tool's documentation](https://pypi.org/project/pypi-attestations/) describe the mechanism and limits; its CLI is explicitly experimental, so the exact version/commands are recorded.

An empty package-index advisory field does not establish that embedded PDFium and every component are vulnerability-free. The [PDFium build documentation](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/README.md) distinguishes JavaScript/XFA build options; generic upstream defaults do not prove the flags of an arbitrary binary.

Source inspection confirms checked absolute library paths, a pinned DLL held against writes/deletion, bounded immutable PDF inputs, a separate worker, timeout and memory budgets. The worker is not an operating-system security sandbox. These mechanisms limit faults and evidence confusion; they are not a universal security guarantee.

Decision: retain the already tested development pin. No application binary was upgraded or launched by this review. Before public distribution, complete the remaining nested-component provenance/build review, vulnerability/version review and dependency-license assessment, then rerun the relevant exact-artifact compatibility checks if the pin changes. This review supplies no legal opinion or release certification.
