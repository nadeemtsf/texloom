# P6 native inspection experiment

The Windows x64 `pdfium_worker` binary inspects PDFs in a separate Rust process. It does not require Python to run. It is not connected to the app's document commit path yet, and this checkpoint does not certify P6 or an installer.

The worker loads one development PDFium DLL by absolute path with restricted Windows library search flags. It verifies the DLL SHA-256 before loading and holds a read handle that disallows writes/deletion. The ABI surface is explicit and bound to that exact binary. PDFium handles close before the library unloads. The application process never loads PDFium through this code.

The JSON request now uses schema 2, a request identity, absolute library path, PDF path, expected PDF SHA-256 and optional `target_marker`. PDF bytes are read with a bound, checked and kept immutable in memory while the document is open. The worker produces page/crop/rotation/annotation metadata, Unicode character bounds, non-text object bounds and opaque-white BGR rasters at scale 2. Output names derive from the private request file, use exclusive creation and cannot overwrite prior evidence. Both the response and inspection bind the request identity and exact request SHA-256. The final response hashes the inspection JSON; the inspection includes PDF, library and raster receipts. These are inspection receipts, not build/revision/operation authorization.

Optional target identity comes from actual PDFium marked-content handles, rather than a visible string or a client rectangle. A single marked-content instance may span multiple text objects. Duplicate/nested identities, marked non-text paint, missing identity, uncovered glyphs and ambiguous target/neighbor coverage are refused. Attribution currently uses conservative character/text-object containment within 0.02 bp. It needs a broader real-engine corpus before native authorization. Form XObjects, unknown paint and nonzero crop origins/rotation are refused; UserUnit and further paint-state/coordinate inspection remain open.

The process bounds request/PDF/object/page/raster sizes. Integration tests launch it through the existing Windows Job Object supervisor with a 10-second timeout and 512 MiB memory limit. They cover invalid schemas/fields/receipts, oversized requests, unpinned DLLs, malformed PDFs, Unicode request paths and refusing output overwrite. A real compiled PDF produces exactly the same page, glyph, non-text and pixel evidence as the pinned reference inspector. Synthetic marked PDFs prove shared versus duplicate marker instances and exact movement versus unrelated neighbor drift. These are headless native tests, not native mouse/typing/IME acceptance.

Development dependency preparation checks both the wheel and DLL SHA-256 and extracts exact archive entries, including the PDFium third-party notice. Python is used only for development preparation/reference tests. The old PDFium 126.0.6462.0 / pypdfium2 4.30.0 pin matches the existing fixture oracle; it is not a decision to ship that version as a runtime dependency. Production dependency review, notices and packaged-artifact acceptance remain required.

The initial worker checkpoint at 10357ff passed all three CI workflows: Windows 41496866570, movement/selection/edit proof 41496866516 and build corpus 41496866661. This includes the three explicitly invoked headless worker tests, release worker build and desktop packaging.

The parent-side `inspection_worker::Worker` now supervises the process and reads only checked evidence. It pins executable/DLL/PDF inputs, binds response and JSON to the exact request, checks every raster checksum/length, confines expected output names to an owned workspace, and rejects incomplete or unexpected targets. It checks cancellation around work and releases derived files when the checked inspection is dropped. Cleanup is flat and never descends into unexpected directories. Configuration is native-only; this API is not exposed through frontend IPC.

The parent checkpoint passes 194 local checks (64 core, 44 build/comparison/worker, 19 native service, 67 frontend). Eight new receipt tests cover replay, corruption, paths, target claims, resource bounds, cancellation and cleanup. Four normally-ignored headless worker tests were separately executed, including a real parent/worker receipt round trip. Linux CI additionally checks symlink refusal. CI for this parent checkpoint is pending.

Next: trusted source-plan and marker binding to project/revision/build/operation, comparison of original/private-zero/candidate PDFs, support for ordinary fractional drag deltas, packaged runtime integration and the complete native signature workflow. Do not treat a frontend boolean, fixture-supplied target IDs or a bare worker `inspected` response as commit authority.

API provenance: the explicit ABI matches the pinned pypdfium2 binding and PDFium's [chromium/6462 edit API](https://github.com/chromium/pdfium/blob/chromium/6462/public/fpdf_edit.h) and [implementation](https://github.com/chromium/pdfium/blob/chromium/6462/fpdfsdk/fpdf_editpage.cpp). The handle/attribution behavior above is additionally tested against the pinned DLL.
